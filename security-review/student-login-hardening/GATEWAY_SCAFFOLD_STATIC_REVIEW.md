# Gateway Scaffold Static Review Findings

**Status:** review-only. Reviewed `supabase/functions/student-access-gateway/index.ts` on `security-review/student-login-hardening`. No deployment or runtime testing performed.

## Good existing safeguards

- The scaffold explicitly fails closed and returns HTTP 503 even if `STUDENT_ACCESS_GATEWAY_READY=true`.
- It does not execute an RPC today.
- It uses a fixed action-to-RPC map rather than accepting an RPC name from the caller.
- It validates the access-code format, method, JSON content type, body size, activity UUID shape, message length, and answer length.
- It restricts browser origins and sets `Cache-Control: no-store`.
- It explicitly warns against logging access codes or exposing privileged keys.

## Issues to resolve before the scaffold can become executable

### 1. No rate limiter is implemented

There is no atomic limiter call. The second hard stop is intentional and must remain until a reviewed limiter is in place before any RPC call.

### 2. Privileged database access is not implemented or constrained yet

The planned code uses a service-role client. Before enabling this, define the exact grants, verify that only the allowlisted RPCs are callable through this path, keep the key in Edge Function secrets, and confirm direct anonymous paths are closed only after all frontend calls have migrated.

### 3. Game ID is shape-checked, not allowlisted

The `start_game_session` action accepts any string matching `^[a-zA-Z0-9_-]{1,100}$`. This does not prove the game exists or is an approved game ID. The database function also needs independent validation against an authoritative allowlist or an authorization rule. This is a separate validation issue; do not silently fix it as part of rate-limiter work.

### 4. CORS headers need a real client compatibility check

The current `Access-Control-Allow-Headers` list includes `authorization`, `apikey`, `content-type`, and `x-client-info`. Before frontend migration, inspect the actual browser preflight generated by the installed Supabase client version and allow only the additional headers that are genuinely required. This must be tested in an isolated environment; do not deploy a diagnostic endpoint to the shared database just to inspect headers.

### 5. Response envelope is still a decision

The planned handler returns `{ data }`, but the existing frontend RPC calls consume the Supabase result directly. A migration adapter must explicitly unwrap or normalize responses to preserve existing behavior: login and list actions expect arrays; `mark_student_messages_read` returns an integer; mutation calls expect row arrays. Do not mix envelope and raw-data conventions.

### 6. Origin checks are not authentication or rate limiting

CORS controls browser cross-origin access; non-browser clients can still call an endpoint. Keep server-side request validation, rate limiting, and database grants as the actual security boundary.

### 7. No trusted-source policy yet

The code does not currently use source headers, which is safer than trusting unverified client-supplied values. A trusted source-level limiter remains undecided. Do not claim IP throttling is active until source metadata semantics are verified.

## Current recommendation

Keep the scaffold fail-closed. Resolve the rate-limiter transaction model, trusted-source strategy, exact RPC grants, game ID authorization, CORS/client compatibility, and response adapter before any code path is enabled. Test the completed function and all student portal workflows in an isolated database first.

No SQL executed; no secrets created; no frontend modified; no function deployed.
