PURPOSE
-------
Move teacher point awards/deductions, reversals, activity score adjustments,
and individual marketplace purchases behind narrow trusted transaction
entrypoints. Browser roles must not be able to write the ledger or protected
activity score columns directly.

A. TRUST BOUNDARY AND ROLE MODEL
-------------------------------
1. Browser roles (anon/authenticated) are untrusted. They must not receive
   direct INSERT on point_transactions or broad UPDATE on
   student_activity_records.
2. A server-side Temmy Gateway authenticates the teacher and derives the
   teacher identity from a verified session. It passes the verified actor
   identity only over a server-to-database credential boundary.
3. A dedicated database role such as temmy_gateway may execute only the
   approved transaction entrypoints. It must not be granted to anon or
   authenticated, directly or through role membership.
4. A separate non-login data-owner role should own SECURITY DEFINER
   transaction functions and have only the table privileges needed by those
   functions. Do not use a superuser as the function owner.
5. Functions must set a fixed search_path (prefer pg_catalog plus explicitly
   schema-qualified application objects), schema-qualify every table/function
   reference, and avoid dynamic SQL unless strictly necessary.
6. The database trusts the gateway role as the authenticated actor boundary.
   A teacher ID parameter is safe only because the function is executable
   exclusively by the trusted server role. Never expose that parameter through
   a browser-callable RPC. Production identity propagation must be designed
   and threat-modelled before implementation.
7. Do not rely on a user-writable custom GUC as proof of actor identity.
   Test-only actor injection must be performed by a privileged test harness
   and must not be copied into production.

C. POINT LEDGER INVARIANTS
--------------------------
- point_transactions is append-only from application paths.
- Positive points represent credits; negative points represent debits/reversals.
  Confirm exact existing conventions and action_type/source values before
  implementation.
- Current spendable balance = sum of signed ledger entries for the student within
  the authoritative class/academic-period scope. Confirm exact deployed conventions
  before production implementation.
- Aggregate points earned are a separate earned-only measure: qualifying positive
  earning entries contribute; marketplace purchases and ordinary deductions do not
  reduce the aggregate. Do not calculate achievement from spendable balance.
- A formal reversal/correction of an incorrectly awarded earning reduces both the
  current spendable balance and aggregate points earned. It corrects the original
  earning and must be linked to that original ledger entry; it is not an ordinary
  deduction. Ordinary disciplinary deductions reduce current balance only.
- If this correction takes aggregate points below an achievement threshold, retain
  the achievement record for history but mark it no longer currently valid for the
  class/academic period; never delete the historical record.
- If a formal correction reduces the aggregate below the milestone that
  originally qualified a student for a leadership position, the previously
  appointed leader retains that post. Do not automatically transfer the post
  or appoint a successor because of the correction.
- Preserve the appointment as an active leadership appointment with its original
  milestone/appointment details. Record the points and achievement correction,
  but do not remove the leader from the post.
- Every applicable ledger entry must carry (or be unambiguously linked to) student,
  class, and academic-period attribution. Never infer historical class attribution
  from the student's current class.
- A student transferred from one class to another (for example, Class 5 to
  Class 6) is enrolled as a new member of the receiving class and starts with
  zero aggregate points and zero spendable balance there, even when the transfer
  occurs during the same academic year and the receiving class has a different
  teacher. Points earned in the previous class end with that class.
- Previous-class points, achievements, transactions, and leadership appointments
  remain attached to the previous class and its teacher's historical records.
  They must not be transferred, carried forward, or counted in the receiving class.
- Each new class/academic-year period starts with its own aggregate points,
  spendable balance, achievements, and leadership appointments; no points or
  active leadership appointments roll forward from a previous period.
- Previous-period points, achievements, transactions, and leadership appointments
  remain accessible as historical records but are excluded from new-period totals,
  rankings, achievement qualification, and leadership eligibility.
- Leadership positions start afresh in each new class/academic-year period. Students
  must qualify again through that period's milestones. Prior appointments remain
  historical and are not active appointments in the new period.
- A cached aggregate/balance summary is optional and non-authoritative; it must be
  reconcilable from ledger entries.
- Never accept a client-calculated balance as authoritative.
- No zero-value transaction is written for a no-op.
- Reversal is a compensating entry linked to the original transaction; the
  original row is never edited or deleted.
- Enforce a unique reversal reference so one original transaction cannot be
  reversed twice.

D. IDEMPOTENCY PATTERN
----------------------
For every mutating operation:
1. Validate request shape and canonicalize all business fields.
2. Compute a payload hash on the trusted server or in a deterministic
   database routine over canonical fields (not arbitrary JSON key order).
3. Insert/claim transaction_requests using a unique request_id scoped to the
   operation/actor. On conflict, lock/read the existing request.
4. If payload hash or actor/operation differs, reject key reuse.
5. If completed, return the stored result without repeating the mutation.
6. If pending, use a defined in-progress/lease strategy; do not blindly run a
   second mutation.
7. Perform the business mutation and persist its final result in the same
   database transaction.
8. A timeout/unknown client outcome is resolved with the SAME request ID.

The exact key scope, pending-state recovery, and payload canonicalization
must be fixed in implementation review.

E. OPERATION ALGORITHMS
-----------------------

E1. award_points(actor, student, amount, reason, request_id)
- Require trusted actor and valid active class ownership.
- Require amount to be a positive integer.
- Read the configured maximum from authoritative server-side configuration (default 50 points per individual manual teacher award; administrator-controlled).
- Reject an amount above the configured maximum with a clear error; never silently truncate. An exceptional above-limit award must pass a separately authorised override workflow and produce an audit record.
- Claim idempotency key.
- Insert one positive ledger row with server-derived teacher identity and
  validated action/source classification.
- Store result and success audit in the same transaction.
- Return transaction ID, awarded amount, and resulting balance.

E2. deduct_points(actor, student, requested_amount, reason, request_id)
- Require positive integer requested_amount and valid ownership.
- Claim idempotency key.
- Serialize against other mutations for the same student's balance (e.g. lock
  a stable student row before calculating ledger sum).
- Compute authoritative balance while holding the lock.
- actual_deduction = LEAST(requested_amount, GREATEST(balance, 0)).
- If actual_deduction = 0, return zero_balance/no-op and write no ledger row.
- Otherwise append a negative ledger entry for actual_deduction.
- Store result and success audit atomically.
- Concurrent deductions must not overdraw or over-deduct.

E3. reverse_transaction(actor, original_transaction_id, request_id)
- Require actor authorization for the original operation/student.
- Claim idempotency key.
- Lock original transaction and student's balance serialization row.
- Reject if already reversed.
- Calculate the full reversal amount required by the original transaction.
- If the full reversal would make available balance negative, reject completely:
  no partial reversal and no ledger entry.
- Otherwise append one compensating entry linked to original transaction.
- When the original transaction is an incorrectly awarded earning, the compensating
  entry reduces both current spendable balance and aggregate points earned. This
  correction must not be classified as an ordinary disciplinary deduction.
- Re-evaluate achievement validity after the correction: if the resulting aggregate
  is below the threshold, retain the achievement row but mark it no longer currently
  valid; do not delete history.
- If the correction reduces the aggregate below the milestone that originally
  qualified the student for a leadership position, the previously appointed
  leader retains that post. Keep the leadership appointment active and preserve
  its original milestone/appointment details; do not automatically transfer the
  post or appoint a successor because of the correction.
- When reversing another eligible transaction type, apply the explicitly defined
  semantics for that operation; do not assume every reversal changes earned aggregate.
- Enforce unique original_transaction_id in reversal records/ledger linkage.
- Save result and success audit atomically.

E4. score_activity(actor, record_id, new_score, notes, request_id)
- Lock the activity record and validate teacher ownership, activity/class
  relationship, student/class relationship, score bounds, and active state.
- old_score = persisted teacher-assigned score.
- delta = new_score - old_score.
- For delta > 0, append +delta.
- For delta < 0, serialize balance and deduct LEAST(ABS(delta), available_balance);
  the activity record still stores new_score even if actual ledger deduction is
  clamped. Return both assigned score and actual point adjustment.
- For delta = 0, write no point transaction.
- Update activity record and any corresponding ledger entry in one transaction.
- Any failure must roll back both.
- Preserve the existing duplicate activity submission behaviour until verified.
  Do not add a unique(activity_id, student_id) constraint as part of this design.

E5. purchase_reward_for_student(actor, student, reward, request_id)
- Process one student per transaction/request. A multi-student UI may issue
  separate per-student requests and aggregate independent outcomes.
- Lock/validate reward and student/balance rows in a consistent lock order.
- Verify reward belongs to actor and is active.
- Lock the reward row and read its authoritative price before evaluating the purchase. If this is the first successful purchase, atomically commit the purchase and permanently lock the price against future edits. A failed purchase must not lock the price. After price lock, a price change is rejected; a different price requires a new reward item. Concurrent price edits and purchases must serialize against this same reward lock.
- If stock is finite, require stock > 0 and decrement exactly once.
  NULL stock means unlimited and is not decremented.
- Serialize student's balance and require balance >= reward price.
- If insufficient balance or out of stock, write no purchase, no debit, and
  no stock decrement.
- Append debit ledger entry, write purchase history snapshot, decrement finite
  stock, and store idempotency result in one transaction.
- Deactivation blocks new purchases but must not delete purchase history.
- A retry with the same request key returns the original per-student result
  without another debit, purchase row, or stock decrement.
- Multi-student processing is independent: one student's failure does not roll
  back another student's already committed purchase.
- Student self-purchases and teacher-initiated individual/group purchases use the
  same trusted per-student purchase operation and the selected student's own balance.
- Marketplace purchase debits affect spendable balance, not earned-only aggregate.

F. LOCKING AND DEADLOCK CONTROL
-------------------------------
- Define one global lock order for operations touching multiple entities.
- Suggested order: idempotency request row -> teacher-owned reward/activity
  row where applicable -> student serialization row -> ledger/purchase/audit
  writes. Validate and refine this order with actual FK/trigger behaviour.
- All paths that mutate one student's balance must use the same serialization
  mechanism; otherwise row locks on different request rows do not prevent
  concurrent overspend.
- Finite stock updates must be conditional/locked so stock cannot become
  negative.
- Add concurrent tests for two deductions, two undo attempts, two purchases
  competing for one stock unit, and simultaneous purchase/deduction for one
  student.
- Retry deadlock/serialization failures only with the same idempotency key and
  bounded retry policy.

G. AUDIT AND ERROR SEMANTICS
----------------------------
- Successful mutation and success audit event commit together.
- A rejected operation that rolls back cannot preserve an audit insert made
  inside that same rolled-back transaction. If rejected-attempt audit is
  required, implement a separate safe logging path with clear failure policy.
- Store safe error codes and minimal metadata; do not expose SQL errors,
  secrets, access codes, tokens, or internal table details to the browser.
- A network timeout after commit is an unknown client outcome, not proof of
  failure. Resolve through the same request ID.
- Per-student marketplace outcomes must distinguish purchased, insufficient
  balance, out of stock, reward unavailable, invalid student/ownership, and
  idempotent replay.

K. APPROVED ACHIEVEMENT AND LEADERSHIP RULES
---------------------------------------------
- Aggregate points are earned-only. Marketplace spending and ordinary deductions
  do not reduce aggregate points; they affect current spendable balance only.
- A formal reversal/correction of an incorrectly awarded earning reduces both
  current spendable balance and aggregate points earned; it corrects the original
  earning and is not an ordinary deduction.
- Ordinary deductions, including disciplinary deductions, reduce current spendable
  balance only and leave aggregate points earned unchanged.
- Achievement thresholds: Bronze 50+, Silver 100+, Gold 150+, Champion 500+.
- The Class Champion ranking title belongs to the student or students with the
  highest aggregate points in the class/academic period, even when that score is
  below 500; this ranking title is distinct from the 500+ Champion achievement level.
- If multiple students tie at the highest aggregate, the teacher administers a
  live task to distinguish the final 1st, 2nd, and 3rd positions. The top three
  receive Champion recognition as 1st-, 2nd-, and 3rd-position awards. The live-task
  result is recorded as the award-ranking outcome and does not alter ledger points,
  achievement thresholds, or milestone-based leadership appointments.
- At each reward-level milestone, the first student to reach that level becomes
  or retains Classroom Captain. The next three qualifying students fill the
  Disciplinary Prefect, Sanitary Prefect 1, and Sanitary Prefect 2 positions.
- Teachers may edit prefect hierarchy titles/order through class-period settings.
- Enforce at most one active leadership position per student within a class and academic year. Reaching another reward-level milestone does not automatically assign the same student a second position.
- If a student who already holds a position reaches another milestone, consider the next qualifying student in the milestone order for the available position.
- A teacher may deliberately change an appointment; preserve the prior appointment history and record the actor and effective time of the manual change.
- Database/server-recorded milestone timestamp determines who reached a level
  first. A deterministic database-generated event sequence resolves identical
  timestamps. Browser clocks are never authoritative.
- Achievement gifts are separate from achievement levels. Reaching a level does
  not automatically grant a gift or debit points; redemption is a marketplace
  purchase using current spendable balance.
- Teachers may upload controlled reward images. Students select only from the
  approved avatar library and cannot upload avatars.


L. STUDENT WITHDRAWAL, SOFT DELETION, AND SAME-CLASS RE-ENROLMENT
-------------------------------------------------------------------
- Same-class temporary absence/withdrawal does not reset the student's
  class-period record when the original record remains. On return, resume the
  same student record and preserve its aggregate points, spendable balance,
  achievements, ledger history, and applicable leadership history.
- Deactivation is reversible: reactivation restores the same student record
  and its preserved history. Do not create a duplicate student.
- Soft deletion is recoverable only within the configured retention/recovery
  policy. If the original record remains recoverable, restore that same record
  after identity and class-period checks; do not create a replacement record.
- A user-interface action labelled "delete" must not be treated as proof of
  permanent erasure. The application and database lifecycle must distinguish
  deactivation, recoverable soft deletion, and legally authorised permanent
  deletion.
- If the student record and associated history have been permanently erased
  under the applicable retention/deletion process and cannot lawfully be
  recovered, a later enrolment creates a new student record with zero
  aggregate points and zero spendable balance for that new enrolment. Do not
  reconstruct erased scores or history.
- Before creating a new record on re-enrolment, check for a recoverable
  original using the approved identity-resolution process. Prevent duplicate
  active membership and preserve an audit event for restoration or new
  enrolment.
- This continuity rule applies only to return to the same class/period. It
  does not override the separately approved class-transfer rule: a receiving
  class starts at zero, while the former class's points, achievements,
  transactions, and leadership history remain attached to the former class.
- Exact retention duration, identity matching procedure, and legal erasure
  workflow remain implementation gates; this review document does not invent
  a retention period or authorise permanent deletion.


I. CLASSROOM RULES — VERSIONED CLASS POLICY (DESIGN ONLY)
---------------------------------------------------------
- Classroom Rules are managed independently for each class by the teacher
  authorised to manage that class. Cross-class or cross-teacher edits require
  a separately authorised administrative permission.
- Teachers may create, edit, reorder, publish, and remove draft rules. A rule
  may contain a title, explanatory text, and optional illustration. Uploaded
  media must follow controlled file-type, size, and storage rules.
- Draft edits do not change the currently published rules.
- Publishing creates an immutable versioned snapshot for the class. Editing
  already-published rules creates a new version; it never overwrites the
  previously published version.
- On first login, and whenever a new version is published for the student's
  current class, the student portal must present the current rules and require
  acknowledgement before allowing access to the normal student portal.
- A student who has acknowledged the current published version is not asked
  to acknowledge that same version again on every login. The student may
  reopen and read the current rules at any time.
- A class transfer evaluates the student against the receiving class's current
  published version and acknowledgement state.
- Acknowledgement must be verified and recorded server-side with the student,
  class, published version, and server timestamp. A browser flag or
  client-supplied timestamp is not authoritative. The login gate must not be
  bypassable by manipulating frontend state or calling portal operations
  directly.
- Preserve every published version and previous acknowledgement for audit.
  Publishing a new version does not erase or rewrite acknowledgements of
  earlier versions.
- Reading or acknowledging rules has no automatic points, reward, or
  disciplinary transaction effect.
- Proposed logical records (names illustrative, not deployed schema):
  classroom_rules (class/owner policy container),
  classroom_rule_versions (immutable published version snapshots),
  classroom_rule_items (ordered rule content within a version),
  student_rule_acknowledgements (student/class/version/server timestamp).
- Final schema, retention, permission matrix, media handling, and exact
  student login integration remain implementation gates. This section is
  design-only and does not authorise a migration or frontend change.
